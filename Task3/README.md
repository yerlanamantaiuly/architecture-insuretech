# Задание 3. Переход на Event-Driven архитектуру

## Текущие проблемы и риски

1. `core-app` и `ins-comp-settlement` зависят от синхронного REST API `ins-product-aggregator`. Если один из внешних API страховой компании отвечает медленно или с ошибкой, задержка распространяется на внутренние сервисы InsureTech.

2. `ins-product-aggregator` выполняет синхронный fan-out во внешние страховые компании: сейчас их 5, после расширения станет 10. При росте числа интеграций увеличатся latency, вероятность частичных отказов, число таймаутов и нагрузка на сам агрегатор.

3. Локальные реплики продуктов и тарифов в `core-app` и `ins-comp-settlement` обновляются polling-запросами. Это создаёт лишнюю нагрузку на `ins-product-aggregator` и не гарантирует одинаковую актуальность данных во всех сервисах.

4. Интервал обновления данных разный: `core-app` запрашивает продукты раз в 15 минут, `ins-comp-settlement` — раз в сутки. Из-за этого расчёты и пользовательские сценарии могут работать с разными версиями продуктового каталога.

5. `ins-comp-settlement` раз в сутки запрашивает у `core-app` все оформленные страховки. Такой batch-запрос становится всё тяжелее по мере роста бизнеса и может перегружать `core-app`, БД и сеть.

6. При сбое суточной выгрузки оформленных страховок появляется риск неполного реестра для взаиморасчётов. Повторный запуск batch-операции может приводить к дублям, если нет идемпотентной обработки.

7. В текущей схеме сложно локализовать ошибки внешних страховых компаний. Один нестабильный партнёр может замедлить обновление всего списка продуктов и тарифов.

8. При росте количества страховых компаний увеличивается сложность retry-логики. Без очередей, dead letter queue и трассировки ошибок часть данных может теряться или долго оставаться неактуальной.

9. Синхронные интеграции хуже масштабируются организационно: каждый новый потребитель продуктовых данных добавит новые REST-вызовы к `ins-product-aggregator`.

10. Нет явного контракта событий и версионирования сообщений. Это повышает риск несовместимых изменений при развитии сервисов.

## Целевое решение

Целевой вариант сохраняет существующую декомпозицию сервисов, но переводит распространение продуктовых данных и оформленных страховок на Event Streaming.

### Поток продуктового каталога

`ins-product-aggregator` остаётся владельцем интеграций со страховыми компаниями. Он периодически и асинхронно получает продукты и тарифы от всех страховых компаний, нормализует данные и публикует события в брокер сообщений.

Основные события:

- `ProductCatalogUpdated` — опубликована новая версия каталога продуктов.
- `ProductTariffChanged` — изменился тариф или условие продукта.
- `InsuranceCompanySyncFailed` — синхронизация с конкретной страховой компанией завершилась ошибкой.

`core-app` и `ins-comp-settlement` подписываются на события продуктового каталога и обновляют свои локальные read-модели. Вместо polling-запросов к `ins-product-aggregator` сервисы получают изменения почти сразу после публикации.

### Поток оформленных страховок

`core-app` остаётся владельцем процесса оформления страховок. После успешного оформления он публикует событие:

- `PolicyIssued` — страховка оформлена и готова к учёту во взаиморасчётах.

`ins-comp-settlement` подписывается на `PolicyIssued` и формирует свой реестр постепенно, по мере поступления событий. Суточный REST-запрос за всеми оформленными страховками больше не нужен.

## Transactional Outbox

Паттерн Transactional Outbox нужно использовать в сервисах, которые публикуют бизнес-критичные события после изменения своих данных:

- `core-app` — для события `PolicyIssued`, чтобы оформление страховки и публикация факта оформления не расходились между собой.
- `ins-product-aggregator` — для событий `ProductCatalogUpdated` и `ProductTariffChanged`, чтобы новая версия каталога не терялась при сбое между записью состояния и отправкой события.

События сначала записываются в таблицу outbox в той же транзакции, что и бизнес-данные сервиса. Отдельный publisher читает outbox, отправляет сообщения в брокер и помечает их как опубликованные. Потребители должны обрабатывать события идемпотентно по `eventId` и бизнес-ключу.

## Брокер и топики

В качестве брокера событий предлагается использовать Kafka-совместимый Event Streaming-кластер. Для задания достаточно зафиксировать логическую роль брокера; конкретная managed-реализация выбирается на этапе инфраструктурного проектирования.

Рекомендуемые топики:

- `product-catalog-events` — события продуктового каталога и тарифов.
- `policy-events` — события оформленных страховок.
- `integration-events` — технические события синхронизации со страховыми компаниями.
- `dead-letter-events` — сообщения, которые не удалось обработать после заданного числа попыток.

Для каждого сервиса-потребителя используется отдельная consumer group. Это позволяет `core-app` и `ins-comp-settlement` независимо читать один и тот же поток событий.

## Требования к надёжности обработки

1. Все события должны иметь `eventId`, `eventType`, `eventVersion`, `occurredAt`, `producer`, `correlationId` и бизнес-ключ.

2. Потребители должны быть идемпотентными: повторная доставка события не должна создавать дубли продуктов, тарифов или записей взаиморасчётов.

3. Для внешних API страховых компаний нужны timeout, retry с backoff и circuit breaker. Ошибка одной страховой компании не должна блокировать публикацию данных от остальных.

4. Для схем событий нужно вести версионирование. Новые поля добавляются обратно совместимо, несовместимые изменения выпускаются новой версией события.

5. Для DLQ нужны алерты и регламент разбора сообщений. Наличие сообщений в DLQ означает, что часть данных не дошла до потребителя.

6. Для наблюдаемости нужны метрики lag consumer group, количества событий, ошибок публикации, ошибок обработки, размера outbox и количества сообщений в DLQ.

## Ожидаемый эффект

- Снижается связность между `core-app`, `ins-comp-settlement` и `ins-product-aggregator`.
- Рост числа страховых компаний с 5 до 10 меньше влияет на внутренние сервисы.
- `core-app` и `ins-comp-settlement` получают обновления продуктового каталога без polling-запросов.
- `ins-comp-settlement` перестаёт выполнять тяжёлую суточную выгрузку оформленных страховок из `core-app`.
- Система становится устойчивее к частичным отказам внешних страховых компаний.
- Появляется контролируемая доставка событий с повторной обработкой, DLQ и мониторингом lag.
